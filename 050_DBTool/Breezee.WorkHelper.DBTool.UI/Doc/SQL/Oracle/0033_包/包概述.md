### 包概述
```
/*包是一组相关过程、函数、变量、常量和游标等元素的组合，它具有面向对象程序设计语言的特点，是对这些PL/SQL 程序设计元素的封装。
包类似于C++和JAVA语言中的类，其中变量相当于类中的成员变量，过程和函数相当于类方法。把相关的模块归类成为包，
可使开发人员利用面向对象的方法进行存储过程的开发，从而提高系统性能。包由两个分开的部分组成：
包定义（PACKAGE）：包定义部分声明包内数据类型、变量、常量、游标、子程序和异常错误处理等元素，这些元素为包的公有元素。
包主体（PACKAGE BODY）：包主体则是包定义部分的具体实现，它定义了包定义部分所声明的游标和子程序，在包主体中还可以声明包的私有元素。
包定义和包主体分开编译，并作为两部分分开的对象存放在数据库字典中*/

/*常量定义*/
const_ok Constant Varchar2(2) := 'OK';

 /*IS TABLE OF ：指定是一个集合的表的数组类型,简单的来说就是一个可以存储一列多行的数据类型。*/
 Type T_SingCol Is Table Of Varchar2(100);
```
### 针对包声明和包体，可以同时保存为一个文件
右击包体，然后点击【编辑说明和体(S)】,即可以同时打开说明和体。上方左边为说明，上方右边为体，然后保存时将说明和体都保存在一个文件中。  
如果我们是右击包体，然后点击【编辑(Q)】，那么就只打开体，保存的文件也只是体；操作也同样适用用说明。

### 在Oracle包的设计中，合理的引用层次和依赖管理是保持代码可维护性的关键
一、分层架构设计原则  
1. 层次划分  
   工具包(PKG_UTL_xx)：为层次1，最底层，无依赖。  
   全局业务包(PKG_GB_xx)：为层次2，仅依赖工具包。  
   模块公共包(PKG_MOD_COMMON)：为层次3，依赖工具包和全局业务包；其中MOD可修改为具体模块简写。  
   模块业务包(PKG_MOD_xx)：为层次4，依赖本模块公共包、工具包、全局业务包；其中MOD可修改为具体模块简写。   
2. 跨模块业务设计策略（3种）  
2.1：服务层模式（推荐）  
  通过创建独立的服务包来处理跨模块业务，避免直接引用其他模块的内部包。  
2.2：事件/消息模式  
  使用队列或表进行模块间通信，完全解耦。  
2.3：接口包模式  
  定义接口规范，各模块实现接口。  

3. 跨模块业务设计模式对比
3.1. 直接引用模式（不推荐）
```
-- 反模式：销售模块直接引用库存模块
CREATE OR REPLACE PACKAGE BODY MOD_SALES_BIZ AS
  -- ❌ 直接引用其他模块的内部实现
  v_stock := MOD_INV_BIZ.get_internal_stock(p_product_id);
END;
```
3.2. 服务层模式（推荐）  
```
-- 通过服务层协调跨模块业务
CREATE OR REPLACE PACKAGE SRV_ORDER_PROCESSING AS
  PROCEDURE process_order_with_inventory(
    p_order_data IN OUT order_data_type,
    p_status OUT VARCHAR2
  );
END;
```
3.3. 事件驱动模式  
```
-- 使用队列解耦模块
CREATE OR REPLACE PACKAGE MOD_SALES_BIZ AS
  PROCEDURE create_order(p_order_data IN order_data_type);
END;

-- 订单创建后，通过队列通知库存模块
CREATE OR REPLACE PACKAGE BODY MOD_SALES_BIZ AS
  PROCEDURE create_order(p_order_data IN order_data_type) IS
  BEGIN
    -- 创建订单
    INSERT INTO orders VALUES (...);
    
    -- 发送库存预留事件
    DBMS_AQ.ENQUEUE(
      queue_name => 'INVENTORY_EVENT_QUEUE',
      enqueue_options => DBMS_AQ.ENQUEUE_OPTIONS_T(),
      message_properties => DBMS_AQ.MESSAGE_PROPERTIES_T(),
      payload => message_type('RESERVE_STOCK', p_order_data),
      msgid => v_msgid
    );
  END;
END;
```
4. 最佳实践总结  
严格分层：确保每层只依赖下层，不反向依赖  
服务层协调：跨模块业务通过专门的服务包处理  
接口定义：为跨模块交互定义清晰的接口  
依赖检查：定期检查包依赖关系  
文档化：记录包之间的依赖关系  
这种设计确保了代码的可维护性、可测试性和可扩展性，避免了循环依赖和紧耦合问题。
